LLM 推理 · 显存

长上下文吃掉的显存，多半是 KV cache

一次 decode 只出一个 token，但每一步都要读前面所有 token 的 K 和 V。把它们留在显存里，是用空间换算力。这笔账可以拆成六个因子，逐个拧。

跳到交互面板

一次 decode 只出一个 token

prefill 一次过完整段 prompt，decode 一次只追加一个 token。显存的压力从第一个 token 起就开始累积。

第 t 个 token 的注意力要看前面每个 token 的 K 和 V。权重不变，那些 K 和 V 就不会变，可以留着。

不缓存就得每步重算。8 个 token 的序列，重算要算 36 次 K/V，留着只算 8 次。

交易的另一头是显存。缓存随 tokens 线性增长，重算的成本随序列长度的平方增长，O(n²)。

缓存里存的是 K 和 V

常驻显存的只有 K 和 V，每层各一份。

每层一份表的形状是 [batch, kv_heads, tokens, head_dim]。K 一张，V 一张。

公式开头的 2 就是这两张表。它不是两次前向，也不是把 K 存了两遍。

q_t、注意力分数、softmax 之后的权重都不驻留，算完即弃。

一个 decode step 的读账

新的 q_t 进来，它和缓存里每个 k 做点积，得到 t 个分数。

softmax 把分数变成 t 个权重，权重再加权混合每一个缓存的 v，得到这一层的 o_t。

读的是整张表，写的只有一行。表每步长一行，读量也每步涨一行。

32 层各做一遍同样的事。读账里权重是常数，表不是。

六个数乘出你的显存

把上面三步写成一行，就是这条公式。

2 × layers × kv_heads × head_dim × tokens × bytes_per_element

六个因子与它们的单位
因子单位它是什么
2张表K 一张，V 一张，不是两次前向
layers层每层各有一份缓存
kv_headshead只数 KV head，query head 不进来
head_dim维每个 KV head 的宽度，元素大小由精度定
tokenstoken上下文里已有的 token 数
bytes_per_element字节fp16 记 2 字节，量化后更小

代入 Llama-2-7B 与 8,192 个 token：2 × 32 × 32 × 128 × 8,192 × 2 字节 = 4.00 GiB。

模型给定 layers、kv_heads、head_dim，上下文给定 tokens，精度给定 bytes_per_element。开头的 2 由 K 和 V 给定，不由你决定。

后面每一节只做一件事，指出一种手段拧的是哪个因子。

512 KiB 有多重

Llama-2-7B 每 token 512 KiB，也就是 16 个格。

decode 是带宽的活

decode 每步的算术量很小，小到盖不住内存访问。

一步要读完所有参数和整张缓存。Llama-2-7B 在 4k 上下文里是 13.04 GiB 权重加 2.00 GiB 缓存，合计 15.04 GiB。

在 2039 GB/s 上，一步 15.04 GiB 只够 126 tok/s；在 3350 GB/s 上是 207 tok/s。两个数都是带宽上限，由公式推得，不是实测。

上下文到 32k，同一步要读 29.04 GiB，带宽上限掉到 65 与 107 tok/s。

权重是常数，缓存不是。上下文越长，缓存越是大头。

结构减法：MHA → MQA → GQA → MLA

最直接的办法是少存几个 KV head。MHA 每层 32 个，MQA 压到 1 个。

MQA 每 token 只留 16 KiB，代价是所有 query head 共用一组 K 和 V，表达能力受挤压。见 MQA。

GQA 取中间，留 8 个 kv head。同样 32 层 128 维，每 token 从 512 KiB 降到 128 KiB，是 4 倍。见 GQA。

同一把尺子上，MHA 的每 token 成本是 MQA 的 32 倍，是 GQA 的 4 倍，是 MLA 的 7.6 倍。

MLA 换了对象：不再按 head 存 K 和 V，每层每 token 存一个 576 维 latent。DeepSeek-V2 的 60 层加起来是 67.5 KiB。见 DeepSeek-V2。

它放弃的是直接可读的 K 和 V。要用的时候得从 latent 投影出来，投影本身要算力。

页首那根 rail 上，kv_heads 与 head_dim 两段在 MLA 下合成一段 latent 576。这不是排版偷懒，是公式里那两项确实不存在了。

公式是下限，不是账单

公式算的是净字节。真实显存里还有分配方式带来的浪费。

按最大长度预留最简单：每个会话先占满一整段，空着的槽也占着显存。

PagedAttention 把缓存切成固定大小的 block，按需发放，空槽回到池子里。见 PagedAttention。

prefix caching 让相同前缀只付一次：同一段 system prompt 在多个请求里复用同一份 K 和 V。

chunked prefill 与 continuous batching 调的是排队和批次，改不了单个 token 的单价。

到这一节 rail 该暗下去了。上面这些都不改因子，只消除浪费。

按住 tokens：滑窗、sink、驱逐

第二类手段直接减少 tokens。

滑窗只保留最近一段 token，更早的 K 和 V 丢掉。Mistral-7B 走的是这条路。见 Mistral 7B。

光有滑窗会崩：开头的 token 一旦被挤出窗口，注意力失去锚点。attention sink 把开头几位固定住。见 StreamingLLM。

H2O 一类按累计注意力权重驱逐不重要的 token，留下的不一定是最近的那些。见 H2O。

三者都把 tokens 按住，代价都是长程召回：被丢掉的 token 不会回来。

按住 bytes：量化 cache

最后一个因子是 bytes_per_element。它也是唯一一个不动模型就能改的因子。

fp16 每元素 2 字节。缓存量化把 K 和 V 压到 1 字节，甚至 0.5 字节。

KIVI 这类做法对 K 和 V 用不同的量化粒度与分组，因为两者的分布不同。见 KIVI。

代价写在精度上：上下文越长，误差累积越明显。

四个要被打死的直觉

四个说法听起来省显存，实际不省。

四条都指向同一个误会：把算力优化当成省显存。

收账：三个旋钮

页面上的所有手段，落到公式上只有三种动作。

六个因子

2 × layers × kv_heads × head_dim × tokens × bytes_per_element

乘积是下限。分配方式决定多付多少。

三个旋钮

  • 压低单价MQA、GQA、MLA、缓存量化
  • 不存两遍分块分配、prefix caching
  • 少存 token滑窗、attention sink、驱逐

前两个动作改因子，第三个动作改 tokens。改不动的那个因子是权重：每步读一遍，与上下文无关。

值得记三个数：每 token 512 KiB，公式开头的 2，decode 受带宽约束。
